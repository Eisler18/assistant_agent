# Evaluation Framework

This document describes the evaluation framework used to validate the LangGraph
time management assistant. It explains required environment variables, CLI
reference, scenario inventory pointers, and how to reproduce evaluation runs

## Required environment

- `LLM_API_KEY` — API key for the LLM provider
- `LLM_MODEL_NAME` — model identifier used for runs (example: `gpt-4o-mini`)
- `LANGCHAIN_TRACING_V2` — set to `true` to enable LangChain/LangSmith tracing
- `LANGSMITH_API_KEY` — API key for LangSmith (optional; metrics are best-effort)

## CLI reference

The evaluation runner is a standalone CLI module. Use the `--dry-run` flag to
validate scenario schemas without invoking the LLM

Schema validation (no LLM calls):

```bash
uv run -m src.evaluation.runner --scenarios create_tests.yaml --dry-run
```

Run a single scenario (smoke test) and write results:

```bash
uv run -m src.evaluation.runner \
  --scenarios create_tests.yaml \
  --scenario create_task_title_only \
  --runs 1 --output results/smoke.json
```

Run a full evaluation (example):

```bash
uv run -m src.evaluation.runner --scenarios create_tests.yaml --runs 5 --output results/create.json
```

Notes:
- Use `--scenario` to iterate a single scenario during development
- The runner creates an independent temporary repository for each run

## Scenario inventory

All scenarios are authored under `src/evaluation/scenarios/` directory
There are multiples files for possible test cases: briefing, routing, creation, updating, reading. Each scenario includes:
- A unique ID (used for reporting)
- A description of the user intent and expected behavior
- A seed for reproducibility (generated by `ensure_seed()`)
- An initial state (optional)
- A sequence of user messages to simulate the conversation
- A list of assertions to check against the final state and messages. Possible assertions include:
  - `repository_task_exists`: checks that a task with specific field values exists in the repository
  - `repository_task_absent`: checks that no task with specific field values exists in the repository
  - `repository_count_delta`: checks that the total number of tasks changed by a specific delta
  - `task_field_equals`: checks that a specific field of a task has an expected value
  - `task_field_date_within`: checks that a date field of a task is within a certain range of an expression (for example, `now` or `planned_at`)
  - `tools_called_include`: checks that specific tools were called during execution
  - `tools_not_called`: checks that specific tools were not called during execution
  - `tool_call_order`: checks that specific tools were called in a certain order
  - `interrupt_fired`: whether the interrupt node was triggered
  - `task_not_saved_before_interrupt`: whether the repository was unchanged before the interrupt
  - `calendar_link_in_response`: whether a Google Calendar link is present in the final messages
  - `content_contains`: whether the final messages contain a specific substring (for example, a reminder about date formats)

## Architectural vs LLM-dependent assertions

- Architectural assertions (deterministic)
  - `interrupt_fired`, `task_not_saved_before_interrupt`, `tools_not_called`
  - These check for internal behavior and are expected to be stable

- LLM-dependent assertions (statistical)
  - `task_field_date_within`, `calendar_link_in_response`, `tools_called_include`
  - These may vary across runs and are reported as pass rates in the JSON report

## Reproducibility and seeds

- Seeds are generated by `src/evaluation/fixtures/seed_template.py` and written to
  `src/evaluation/fixtures/seed.json` by `ensure_seed()` when needed

## LangSmith integration

- LangSmith metrics are optional. If `LANGCHAIN_TRACING_V2` is enabled and the
  `LANGSMITH_API_KEY` is available, the runner will attempt to collect token and
  latency metrics per run and include them in the JSON report
